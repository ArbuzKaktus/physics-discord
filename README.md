# Автономная передача видео по радио

Дата исследования: 30.09.2026. Подбор для покупки в России, цены в рублях. Доставку, инструменты и стоимость разработки бюджет не включает. Проектирование выполнено по архиву `2.zip`; аппаратных измерений на выбранных платах ещё нет.

## 1. Рекомендуемое решение и стоимость

Два узла на Orange Pi Zero 3 1 GB и двух обычных nRF24L01+ с печатными антеннами. Камера подключается непосредственно к передающей плате по USB. H.264 кодируется на этой Linux-плате. Приёмная Linux-плата сама восстанавливает и декодирует поток, выводит изображение через HDMI. ПК нужен только для подготовки образов и разработки, во время демонстрации не требуется. Wi-Fi, Bluetooth и мобильная сеть для передачи между узлами не используются.

Сначала реализуется одно направление видео A→B с обратными подтверждениями и командами. Два видеопотока A↔B — дополнительный этап на том же оборудовании с разделением времени. Это полудуплексный радиоканал; одновременный просмотр двух потоков возможен благодаря буферизации, но два модуля не передают и не принимают одновременно.

Ориентир бюджета:

| Сценарий | Бюджет |
|---|---:|
| Одностороннее видео, имеющийся телевизор/HDMI-монитор | 20–22 тыс. ₽ |
| Одностороннее видео, покупка собственного 7-дюймового HDMI-экрана | 26–29 тыс. ₽ |
| Два направления видео, два новых экрана и две камеры | 34–38 тыс. ₽ |

Эти интервалы включают оценочные кабели, охлаждение и монтаж. Если уже есть подходящие блоки 5 В/3 А, карты и камера, бюджет заметно уменьшается. Имеющийся телевизор не делает систему зависимой от ПК. Работа от розетки автономна по вычислениям; аккумуляторы в базовую комплектацию не входят.

## 3. Совместимость

| Узел | Интерфейс и решение |
|---|---|
| Радиомодуль → Orange Pi | SPI1, 3,3 В логика, отдельные CE и необязательный IRQ |
| Камера → передатчик | USB-A; A4Tech заявляет UVC и Linux ≥2.6, выход MJPEG |
| Linux → H.264 | FFmpeg/libavcodec + libx264, программный энкодер |
| Приёмник → экран | micro-HDMI платы → HDMI экрана |
| Радиодрайвер | C++ RF24, Linux spidev + GPIO character device; проверить соответствие gpiochip/offset |
| Веб-интерфейс | Сервер работает на Linux-плате, камера и кодек не зависят от внешнего браузера |

USB-камера этой сборки не CSI. Камеры Raspberry Pi на шлейфе и ESP32-CAM не являются прямой заменой USB UVC-камеры. У Orange Pi Zero 3 нет необходимого разъёма камеры для штатного подключения Pi Camera. Не обещать аппаратный H.264 encode H618: GPU/видеодекодер и аппаратный энкодер — разные блоки; базовый вариант не зависит от наличия последнего. Производительность libx264 на 256×128 ожидается достаточной по инженерной оценке, но должна быть измерена с одновременной работой радио и UI.

## 4. Подключение и пайка

### Таблица для обоих узлов

Это номера **физических контактов 26-pin Orange Pi Zero 3**, а не GPIO BCM Raspberry Pi. Сверять с маркировкой pin 1 и ревизией своей платы. Указанные сигналы взяты из руководства производителя Orange Pi Zero 3.

| nRF24L01+ | Orange Pi Zero 3 | Назначение |
|---|---|---|
| VCC | Физический pin 1, 3,3 В | Питание обычного модуля |
| GND | pin 6, GND | Общая земля |
| SCK | pin 23, PH6, SPI1_CLK | Тактирование SPI |
| MOSI | pin 19, PH7, SPI1_MOSI | Orange Pi → радио |
| MISO | pin 21, PH8, SPI1_MISO | Радио → Orange Pi |
| CSN | pin 24, PH9, SPI1_CS | Аппаратный chip select SPI1 |
| CE | pin 7, PC9 | Управление режимом TX/RX |
| IRQ | pin 11, PC6, при использовании прерывания | Активный низкий уровень; на первом тесте можно не подключать |

MOSI соединяется с MOSI, MISO с MISO. На некоторых карточках продавцов эти линии ошибочно предложено перекрестить. CE подключается к управляемому GPIO, не постоянно к питанию. Не путать CE радиочипа и CSN.

Параллельно VCC–GND радио установить 47 мкФ и 100 нФ, максимально близко к модулю. Плюс электролита — к VCC, полоска минуса — к GND. **На обычный nRF24L01+ нельзя подавать 5 В**. Восьмиконтактная распиновка стандартного модуля и Trema-модуля отличаются: Trema имеет свой стабилизатор и вход 5 В; таблица выше относится к выбранному обычному модулю.

Если питание 3,3 В нестабильно, поставить отдельный адаптер-стабилизатор nRF24L01+ с входом 5 В и выходом 3,3 В: 5 В взять с pin 2, землю оставить общей. Перед подключением радио измерить выход. Его цена/наличие не включены в подтверждённые позиции. PA+LNA потребляет больше и требует более тщательного питания; для аудитории он не нужен.

### Порядок сборки

1. Полностью отключить питание. Проверить ориентацию контактной гребёнки по рисунку именно Zero 3 и отметке pin 1. Не использовать картинки Raspberry Pi как нумерацию GPIO.
2. При необходимости припаять гребёнку 2×13: сначала крайние контакты, проверить вертикальность, затем остальные. Регулируемый паяльник, чистое жало, флюс для электроники; ориентир 320–350 °C для обычного припоя, корректировать по припою. Не держать жало на площадке долго; кислотный флюс не использовать.
3. Установить радио в съёмный разъём. Провода SPI желательно 3–5 см, для первичной макетки не более 10 см. Длинный Dupont обрезать при переходе к финальной сборке. Не паять антенну и не менять её дорожки.
4. Припаять конденсаторы и провода на перфоплату. Прозвонить GND, питание и каждую сигнальную линию; проверить отсутствие перемычек припоя. Не соединять земли двух удалённых узлов проводом: общая земля нужна внутри каждого узла.
5. Разместить антенну радио за краем основной платы, вдали от радиатора, металлического корпуса и проводов. Для первых тестов расстояние между модулями 1–2 м и минимальная мощность; не складывать антенны вплотную.
6. Установить охлаждение, проверить отсутствие короткого замыкания, измерить 3,3 В на разъёме перед установкой радио. Включать и снимать радио только при отключённом питании.
7. Камеру вставить в USB-A передатчика. Экран подключить через HDMI к приёмнику и запитать по его инструкции. Разъём GPIO экрана к Orange Pi не подключать.
8. Для постоянной сборки закрепить платы на стойках, сделать разгрузку USB/HDMI кабелей. Завершать Linux корректно перед отключением питания.

Инструменты: мультиметр, регулируемый паяльник, припой/флюс для электроники, кусачки, пинцет. Они не включены в цену системы.

## 5. Подготовка Linux и проверка

Использовать конкретный официальный Debian/Ubuntu-образ **для Orange Pi Zero 3**, сохранить номер версии и контрольную сумму. Образ Raspberry Pi OS не подходит. На передатчике достаточно минимального образа; на приёмнике нужен вывод на HDMI. Не запускать браузер на передатчике ради захвата камеры.

1. Записать ОС на обе microSD. Подготовить роли A/B и конфиг. Компьютер допустим для прошивки, но после запуска отсоединяется.
2. В образе с orangepi-config включить SPI1 через System → Hardware, сохранить и перезагрузить. В руководстве указан `/dev/spidev1.1`; на другом ядре проверить фактический узел, не захардкодить `/dev/spidev1.0`. Встроенная SPI Flash использует другой интерфейс; не обращаться к ней как к радио.
3. Проверить `ls /dev/spidev*`, `gpioinfo`, `v4l2-ctl --list-devices`, `v4l2-ctl --list-formats-ext`. Для loopback SPI временно снять радио, соединить MOSI с MISO и выполнить spidev_test; потом убрать перемычку.
4. В RF24 явно выбрать Linux SPIDEV и правильный gpiochip. GPIO PC9 имеет старый глобальный номер 73, но **73 нельзя слепо считать offset любого gpiochip**: определить line/chip по своему ядру. SPI bus 1, CS 1 обычно соответствует аргументу 11 в конструкторе RF24; сверить с выбранным узлом. Pin 7 не является GPIO7 в этой нумерации.
5. SPI mode 0, 8 бит, сначала 1 МГц, далее 4–8 МГц при устойчивой работе. Максимум SPI чипа 10 МГц. На обоих радио задать одинаковые адрес, скорость, канал и CRC16. Начать с 1 Мбит/с для проверки, затем измерить 2 Мбит/с.
6. Проверить обмен короткими пакетами, затем тест потока без камеры. Отдельно измерить частоту повторов, потери, скорость и задержку. Приёмный поток должен быстро опустошать FIFO; C++ предпочтителен для рабочего драйвера.
7. Проверить USB-камеру и энкодер без радио. Сначала 640×480 вход, уменьшение до 256×128 и 10 FPS; кодирование libx264 ultrafast/zerolatency, без B-кадров, GOP около 10–20 кадров. Проверить наличие libx264 в установленном FFmpeg. Результат отправлять в приложение через pipe/libavcodec, разделяя H.264 на полные access units.
8. После независимых тестов соединить медиапроцесс и радио. Установить systemd-службы с автозапуском/перезапуском, конфигами и ограниченными логами. Отключить Wi-Fi/BT через подходящий для образа механизм и подтвердить это перед показом.

RF24 поддерживает Linux и Pico SDK, но готовность конкретного Orange Pi GPIO backend нельзя предполагать без проверки. Если Linux-планировщик не позволяет стабильно обслуживать 3-пакетный FIFO, резерв: вспомогательная Pico на каждом узле через USB, радио подключается к ней. Главные Linux-платы по-прежнему кодируют/декодируют автономно. Доплата — от 1 880 ₽ за две Pico плюс USB-кабели/хаб; это запасной вариант, а не обязательная покупка.

## 6. Радиоканал и реалистичные показатели

nRF24L01+ — пакетный трансивер 2,4 ГГц, физическая скорость 250 кбит/с, 1 или 2 Мбит/с; пользовательская полезная нагрузка одного пакета максимум 32 байта. У каждого TX/RX FIFO только три позиции. CRC/ACK/повторы, SPI и паузы Linux уменьшают доступную скорость.

Оценка проекта, которую надо проверить: 256×128, цвет, 10 FPS, H.264 50–70 кбит/с на спокойной сцене. 15–20 FPS — экспериментальная цель; при движении качество на том же битрейте снизится. Частота кадров не вычисляется напрямую из битрейта H.264. На 70 кбит/с и 10 FPS средний сжатый кадр около 875 байт, но I-кадр значительно крупнее.

Для предлагаемого заголовка 8 байт остаётся 24 байта данных. Поток 70 кбит/с требует около `70 × 32/24 = 93,3 кбит/с` принятой 32-байтной нагрузки радио, плюс метаданные. Если измерено 300 кбит/с такой нагрузки, видеоданные после заголовка получают максимум около 225 кбит/с до прочих расходов. Если измеренные 300 кбит/с уже относятся к видеобайтам, второй раз умножать на 24/32 нельзя.

Два потока по 70 кбит/с требуют суммарно минимум 186,7 кбит/с радионагрузки, дополнительно нужны метаданные, переключения, управление и запас на повторы. Это объясняет возможность TDD, но не гарантирует её. В ТЗ измерять goodput на уровне полностью восстановленных видеобайт; 300 кбит/с не считать обещанной характеристикой комплекта.

Для стенда использовать частоту внутри 2,400–2,4835 ГГц, с запасом от краёв при 2-Мбит/с режиме; не пользоваться всем аппаратным диапазоном 2,400–2,525 ГГц только потому, что его позволяет регистр. Конкретный разрешённый канал и мощность выбираются для места демонстрации. Нет обещания «100 метров видео» по рекламной дальности модулей.

| CMake-флаги Cortex-A9/armv7/NE10 | Сделать новую сборку arm64/Linux, без принудительных флагов старой платформы |

В исходнике формат v2 имеет `VID_APP_BYTES=259`: CRC32 4 байта + RS-блок 255 байт. Это не пакет NRF. Простое изменение константы на 32 ломает layout и декодер. Туннелирование старого формата в 32-байтных пакетах возможно, но создаёт лишние накладные расходы и не выбрано как основной транспорт. `VIDEO_PACKET_PIPELINE.md` прямо обозначен устаревшим: старый формат v1 не использовать.

## 8. Техническое задание

### 8.1. Название и назначение

«Автономный учебный стенд передачи цифрового видео по пакетному радиоканалу 2,4 ГГц». Назначение — демонстрация захвата, сжатия, пакетизации и восстановления видео, исследование влияния параметров радиоканала на скорость, потери, задержку и качество.

### 8.2. Состав и границы

Две Linux-платы, два радиомодуля, одна USB UVC-камера, HDMI-экран приёмника и питание. Одна дополнительная камера/экран для двустороннего этапа. ПК и Интернет во время работы не требуются. Основной источник изображения — USB-камера передатчика, поэтому открытый браузер телефона/ПК не нужен для работы.

Обязательные режимы: радиотест без видео, видео A→B, повторный старт после обрыва. Дополнительные: видео B→A с перестановкой ролей; два независимых потока через TDD. Звук, HEVC, мобильная сеть, облачные сервисы и дальность сотни метров вне первой версии.

### 8.3. Программная архитектура

Передатчик: V4L2 USB → уменьшение/ограничение FPS → libx264 → ограниченная очередь access units → фрагментатор → RF24/SPI.

Приёмник: RF24/SPI → проверка нумерации/дубликатов → сборка полного access unit → CRC32 записи → FFmpeg H.264 decode → HDMI и локальный web UI.

Процессы/модули: `media_tx`, `radio_link`, `frame_reassembler`, `media_rx`, `web_manager`, `metrics`. Интерфейс радиотранспорта должен принимать байтовые записи и не зависеть от H.264. Основной язык C++17; CMake; FFmpeg/libavcodec/libavformat/libswscale, RF24, GPIO character API. Зафиксировать версии ОС и библиотек в итоговом репозитории.

### 8.4. Протокол первой версии

NRF использует фиксированные 32-байтные payload и аппаратный CRC16. Внутренний заголовок:

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 1 | Версия и тип: video/control/test |
| 1 | 1 | Session ID |
| 2 | 2 | Frame/record ID |
| 4 | 2 | Fragment index |
| 6 | 1 | Flags: START/END/KEYFRAME и резерв |
| 7 | 1 | Длина данных: 0–24 |
| 8 | 24 | Данные записи; неиспользованный хвост заполняется нулями |

Многобайтовые поля — little endian. Frame ID увеличивается с модульным сравнением при переполнении; новый сеанс очищает все незавершённые кадры. Session ID назначается при handshake; после 256 сеансов нельзя полагаться на него как на уникальный идентификатор без очистки состояния.

Полная видеозапись содержит длину H.264 access unit (uint32), timestamp (uint64, мкс), width/height (uint16 каждый), признак keyframe (uint8), данные H.264 и CRC32 всей записи до CRC. Метаданные входят в данные фрагментов; сборщик проверяет START, индексы, END и точную длину. Максимальный access unit 16 КиБ, максимум 4 незавершённых записи, проверка всех длин до выделения памяти. Параметры таймаутов конфигурируемые; стартовый срок сборки 500 мс, уточнить по измеренному goodput и размеру I-кадра.

Разрешить bounded auto-ACK/auto-retry, первоначально 3 повтора; конечные параметры выбирать по стенду. ACK радио подтверждает получение трансивером, но не декодирование кадра приложением. При MAX_RT контролировать сброс/удаление просроченного payload, не оставлять TX FIFO заблокированным. Пропавший фрагмент означает потерю всего access unit; неполные данные декодеру не передавать.

После утраты зависимого кадра приёмник запрашивает новый IDR и ожидает корректный ключевой кадр. Передавать SPS/PPS с IDR. Для исходящего потока ограничивать очередь по возрасту; при перегрузке сбрасывать зависимую цепочку и генерировать IDR, а не произвольно выбрасывать P-кадр и продолжать его потомков. Управление в обратном направлении — короткие ACK payload/служебные окна, с явным подтверждением command ID. Периодический IDR обеспечивает восстановление даже при потере команды.

FEC не обязательна в MVP. Следующий эксперимент — XOR на уровне групп пакетов или код стираний; стоимость и эффект измерить. Не переносить автоматически старое RS на поток NRF.

### 8.5. Параметры видео

Обязательный стартовый профиль: H.264, yuv420p, 256×128, 10 FPS, номинальный битрейт 50–70 кбит/с, Annex B, без B-кадров, low latency, ключевой кадр каждые 1–2 с и по запросу. Камера может захватывать 640×480; масштабирование/кадрирование выполняется до кодирования. 256×128 искажает кадр 4:3, поэтому выбрать crop или letterbox, не растягивать без настройки.

Битрейт ограничивать VBV/maxrate/bufsize, а не только средним target bitrate; размеры ключевых кадров и колебания нагрузки учитывать в очереди. Слабый канал: профиль 128×96, 5–10 FPS и 20–40 кбит/с. Высокий профиль: 256×128, 15–20 FPS — необязательный результат измерений, не условие сдачи.

### 8.6. Веб-интерфейс и автономный вывод

На каждой плате сервер предоставляет start/stop, роль, канал, скорость RF, мощность, разрешение/FPS/битрейт, состояние камеры, загрузку CPU, очередь и статистику потерь. Полученное видео показывается в локальном браузере приёмника на HDMI в режиме kiosk. Можно декодировать H.264 на сервере и отдавать MJPEG только локальному UI: это не увеличивает радиобитрейт и не требует WebCodecs. На 1 GB проверить потребление памяти браузера; предусмотреть лёгкий native viewer как резерв вывода.

Для сохранённого WebCodecs-плеера нужны поддерживаемый H.264 codec config и secure context: HTTPS с доверенным сертификатом или loopback localhost. Простой HTTP по LAN-IP не является надёжным способом получить доступ к камере/WebCodecs. При этом базовый аппаратный источник видео на Linux не зависит от разрешений браузера.

Доступ с телефона необязателен. При полном запрете Wi-Fi подключать локально по Ethernet через совместимый USB-OTG Ethernet-адаптер телефона. Поддержка телефона/адаптера должна проверяться отдельно. Если преподаватель разрешит локальный Wi-Fi только для управления, он может обслуживать UI, но радиолиния A↔B всё равно NRF. По умолчанию Wi-Fi выключен. Не соединять A и B общей Ethernet-сетью во время демонстрации передачи, чтобы исключить обход радиоканала.

### 8.7. Дополнительный TDD-режим

Узел A — координатор, B — ведомый. Координатор выделяет ограниченные по времени/числу пакетов окна передачи A и B. Синхронизация/передача разрешения, защитные паузы и подтверждения входят в протокол; B не начинает TX без действительного разрешения. Потеря синхронизации переводит B в приём, A восстанавливает сеанс. Не переключаться по несинхронизированным таймерам двух Linux-процессов. Длину окон подобрать по измерениям, первоначально 10–20 мс полезного окна с отдельным запасом на управление и планировщик.

Вначале два потока по 30–40 кбит/с, 5–10 FPS. Профиль 70 кбит/с в обе стороны разрешать лишь после теста достаточной суммарной ёмкости с запасом. Если критерии не выполняются, сдаётся обязательный односторонний режим; аппаратная схема остаётся пригодной для исследования TDD.

### 8.8. Критерии приёмки

| Проверка | Критерий |
|---|---|
| Автономность | После включения обе системы запускаются без ПК/Интернета; камера физически на передатчике; изображение на HDMI приёмника |
| Радиотранспорт | На 1–2 м, 2 Мбит/с RF, 60 с измерения: минимум 120 кбит/с восстановленных тестовых данных после заголовков; иначе доработка драйвера/снижение профиля |
| Основное видео | 256×128, задано 10 FPS, отображается ≥8 FPS в среднем на спокойной освещённой сцене, 10 минут на расстоянии 3 м прямой видимости |
| Задержка | Не более 1 с для 95% измерений базового профиля; измерять видеосъёмкой источника/экрана или синхронизированными часами, а не вычитать несогласованные timestamps |
| Восстановление | После 3-секундного отключения радио видео возвращается не позднее 3 с после восстановления связи |
| Ошибки | Обрыв/дубликаты/неверные длины не вызывают зависания, роста памяти или передачи неполного кадра декодеру |
| Отсутствие обхода | Wi-Fi/BT/мобильный канал отключены; нет проводного A↔B; отключение NRF прекращает удалённое видео |
| Память и нагрев | 10 минут без OOM и неконтролируемого роста очередей; записать CPU, память и температуру |
| Дополнительный TDD | Два потока по 30–40 кбит/с, ≥5 FPS каждый, 5 минут; измерить отдельно обе стороны |

Видеопрофиль 256×128/10 FPS — проектная цель стенда, а не уже проверенная гарантия покупки. Если первый измерительный этап показывает меньшую пропускную способность, сначала устранить обслуживание FIFO/питание, затем официально зафиксировать сниженный профиль с преподавателем.

### 8.9. Физический эксперимент

Измерить зависимость goodput, PER, повторов и задержки от расстояния (1/3/5/10 м), скорости RF (250 кбит/с, 1/2 Мбит/с), мощности, ориентации антенны, препятствий и выбранного канала. Одинаковое освещение/тестовая сцена, не менее трёх повторов по 60 с на комбинацию, фиксировать условия и загрузку CPU.

NRF имеет RPD — пороговый индикатор наличия сигнала, а не полноценный измеритель RSSI/SNR. Не выводить числовой SNR из старого проекта и не выдавать долю потерянных пакетов за BER. Плохие CRC аппаратно отбрасываются: стенд измеряет PER/доставку, а прямой BER по принятым исправным пакетам недоступен.

Для интерпретации использовать λ≈12,5 см при 2,4 ГГц, влияние экранирования, отражений и ориентации. Свободнопространственное затухание — только приближение: аудитория даёт многолучевое распространение. Дальность не выводить из этой формулы без измерений.

### 8.10. Этапы и результаты

1. Linux, питание, камера, HDMI, SPI и проверка радиочипов.
2. Тестовый транспорт без видео; таблица goodput/PER; решение о профиле и необходимости вспомогательной Pico.
3. Кодирование/декодирование и новый фрагментный протокол.
4. Сквозное одностороннее видео, восстановление, автозапуск и web UI.
5. Монтаж, физические измерения и отчёт.
6. Дополнительные камера/экран и TDD после успешного MVP.

Результаты разработки: репозиторий C++17, воспроизводимый образ/инструкция установки, схема с распиновкой, BOM, описание wire protocol, конфиги A/B, службы systemd, протокол приёмки, CSV измерений и графики, демонстрационная запись. Исходник рабочего проекта остаётся отдельным: университетская версия имеет собственную сборку и радиобэкенд.
